### Mechanism

- `flask_app/csrf.py` is in-house, built on `secrets.token_urlsafe(32)` and `hmac.compare_digest`. No dependency was added, and `requirements*.txt` are unchanged. `csrf.init_app(app)` in `flask_app/__init__.py` registers a `before_request` check and a `csrf_token()` Jinja global.
- `csrf_token()` stores the token in the signed session the first time a page renders it. The token is stable for the session, so several open tabs keep working. It is not rotated on login or logout.
- The check applies to every request whose method is not GET/HEAD/OPTIONS/TRACE and that matches a route. Unrouted requests keep their 404/405. It runs before the view and its auth decorators, so a forged anonymous write gets 403 instead of 401 or a redirect.
- Where the token is read from:
  - the `X-CSRFToken` header;
  - the `csrf_token` form field, for urlencoded or multipart bodies;
  - for the `track_watch_time` endpoint only, a `csrf_token` field in a JSON body. The raw body is parsed with `get_data(cache=True)` and `json.loads`, so the handler's own content-type handling, and with it the T09 defect, is unchanged.
- Denial for endpoints outside `FORM_ENDPOINTS`, and for `X-Requested-With: XMLHttpRequest` requests: 403 JSON `{"error": "CSRF token missing or invalid"}`.
- Denial for HTML form endpoints: 403 with the film or article base page and the flash message "Your session expired or the form was invalid. Please reload the page and try again."
- Templates: both base templates define `const CSRF_TOKEN = {{ csrf_token()|tojson }};` in `<head>`. `articles/base.html` installs a `jQuery.ajaxPrefilter` that adds the header to same-origin writes other than GET/HEAD/OPTIONS.

### Limitations

- **GET `/logout` remains unprotected.** Both base templates log out with links. Turning them into POST forms would change visible navigation, which is a non-goal. A forged cross-site GET can therefore log a user out, but it cannot write data. Follow-up: switch the links to POST forms and drop GET from the route, in T05 or T06.
- After deploy, a page that was already open has no token, so its writes fail with 403 until it is reloaded. Sessions that are still valid get a token on their next page render; nobody is logged out.
- Login and registration denials always render the article base page, because their path is `/login` or `/register`, even when the user came from the film room.
- The token protects against cross-site forgery only. Script running on the site's own pages (slice 2) could read it. Tests use Flask's test client, not a browser, so real cross-site browser behaviour, SameSite cookies, and the CKEditor and beacon browser paths are not exercised.
- Not in this slice: sanitization (slice 2), uploads and request size (slice 3), the T09 string-beacon content type, and any migration.
