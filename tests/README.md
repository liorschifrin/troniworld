# Regression coverage

Run the README commands from the repository root with Python 3.12 and Node 22 (for isolated JavaScript render tests). Tests use Flask's test client, never the running server. Authentication fixtures place synthetic user IDs in signed sessions; they test authorization, not the shared-password login flow. Admin and leadership are separate roles.

Passing gates cover anonymous login redirects on film pages and JSON 401 on the film comment API; ordinary/leadership point-edit and nonowner-delete denial without mutation; admin point editing; main comment API author/recipient/nonrecipient visibility; hidden-game list filtering; fresh schemas/SQLite foreign keys; temporary upload storage; and configuration isolation guards.

`test_visibility.py` (T03, 137 cases) covers the reachable rows of the [visibility policy matrix](../docs/visibility-policy.md): main film comment visibility (including inherited reply privacy, author-only and malformed `private_to`), hidden-game responses byte-identical to missing-game responses without writes, hidden-game exclusion from lists/my-games/team data/option lists, notification creation and read isolation, admin report counts, and admin-only route access for anonymous, ordinary, leadership, and admin callers. It also verifies the retired `/api/v1/games` route returns 404 for anonymous and admin callers. Q1 option A means leadership/admin flags grant no extra private access. Synthetic tests cover admin author/recipient/nonrecipient and leadership-author combinations, hidden-game ancestors, depth-two notification chains, notification edit history, and unchanged admin writes/watch behavior on visible and hidden games.

Current gates (Python 3.12, Node 22, synthetic in-memory SQLite): **725 passed, 1 deselected** with `-m 'not known_failure'`; **1 xfailed, 725 deselected** with `-m known_failure`, no XPASS. `python -m pip check` is clean.

`test_csrf.py` (T05 slice 1, 194 cases) covers all 31 write requests on the 28 state-changing routes. A route-map test fails if a new write route is not listed. Each write is sent the way its real client sends it (form field, `X-CSRFToken` header, or beacon body field) with a server-minted token, and must succeed and change data. Logout must clear the session. Each write is then forged four ways: no token, a wrong token, a valid token from another session, and a victim session with no token. Every forgery must return 403 (JSON error or flashed HTML page), and the snapshot of every table, every upload, and the login state must be unchanged. The file also checks: malformed tokens; that tokens in the query string or a cookie are denied; that a body token is read only for the beacon; that the token rotates at login and register (the old token is denied) and is kept at logout; that GET pages and GET `/logout` work without a token; that 404/405 are unchanged; and that 13 rendered pages carry the session token in `CSRF_TOKEN` and in every POST form. A source scan pins the template inventory (20 fetch writes, 14 POST forms, 1 beacon, 3 jQuery posts) and checks that each one carries the token. The shared `client_for` fixtures put a token in the session and send it on every request, as a page from this site would; only `test_csrf.py` sends requests without a token. Tests use Flask's test client, not a browser. Real cross-site browser behaviour and cookie policy are not exercised.

T04 adds 350 API cases (335 initially, 15 in review round 1) in `test_input_validation.py` and 19 handler cases in `test_handler_escaping.py`, and turns its two former strict xfails into normal passing tests. Rejection checks snapshot row counts and all values in every table, including notifications/roster associations; valid controls cover every writing route, fractional/boundary/null timestamps, no comment length cap, legacy client `author_name`, and one-level replies. Existing T03 deep-reply tests now seed legacy rows directly because new depth-two writes are forbidden. New typed writes do not change legacy read policy.

Handler tests parse Jinja-rendered HTML and execute the actual JavaScript rendering functions in Node with minimal DOM stubs. They decode HTML attributes before checking handler source, exercise hostile stored usernames/comment text/timestamps, and verify escaped data attributes. No browser, YouTube player, or Flask server runs. CI installs Node 22 explicitly. The remaining handler sites were source-inspected: film/article edit/delete/reply actions use database integer IDs; privacy-chip handlers use array indices; notification handlers read attributes; comment text uses `escHtml`/`parseMentions` or article `esc`; point handlers validate timestamps; username autocomplete reads escaped data attributes.

T05 slice 2 adds 196 cases in `test_sanitize.py` using synthetic markup. 33 hostile fixtures (script tags, event handlers, `javascript:`/`data:`/`vbscript:` URLs, style/class/id, iframes, tables, media embeds, comments, broken nesting, image sources outside `/static/uploads/<name>` including percent-encoded traversal, subdirectories, and query strings) are checked three ways: the sanitizer output, the rendered post page for a stored row (the stored value stays unchanged), and the stored value after create and edit. Each allowed tag and link form (http, https, mailto, relative, fragment) must survive. `CKEDITOR40` holds 19 fixtures written by hand from the CKEditor 5 classic 40.2.0 output format: italic `<i>`, headings as `h2`–`h4`, lists, links, quotes, soft breaks, block, inline, and alt-text images with their `figure`/size attributes, captions, tables, and media. They are checked as sanitizer units and as a full document that is rendered, created, and edited. Captions and tables trigger the "removed" flash. Disallowed-only content gets its own message, and empty content (no text and no image with a source) gets the required message. The edit form loads sanitized, escaped markup, and the editor pages drop tables and media embeds. No template applies `safe` to `post.content`, and article comments stay escaped. Pre-change comparison: on `fd38ed8` (before the review repair) **55 failed, 141 passed**; on `db660df` **191 failed, 5 passed** (74 ImportError-only; the 5 passes are controls). No browser runs, so the fixtures are not captured from a live editor.

The only strict expected failure reproduces this audit observation:

- T09: JSON string beacon sent as text/plain returns 500. The invariant allows a deliberate 4xx rejection or successful handling; it does not choose a future client/server contract.

Each expected failure accepts only `AuditRegression` from the specific invariant after ordinary setup/response assertions. Unexpected success fails CI. Do not broaden markers to cover arbitrary assertions or exceptions. `python -m pytest --runxfail -m known_failure` exposes the remaining beacon failure for diagnosis and intentionally exits nonzero on the current baseline.

The former T03 strict cases now pass and live in `test_visibility.py`; the two T04 cases pass in `test_known_failures.py` without strict/known-failure markers.

Not covered by the visibility suite: T03a leadership-group audiences (proposal only); T05 upload content validation (slice 3); T06 login/identity; T07 migration replay; T08 user deletion with history; T09 browser races, general read-state/count semantics and pagination (retained edit history and admin report count consistency are covered here); CSV import; the audit's thirteen-page/twenty-template smoke sweep; browser/YouTube interactions, accessibility, load, deployment, or other database engines. Current-schema `create_all()` is not evidence of successful migrations. The synthetic image upload checks storage routing only, not image validity.

These tests cover the implemented T03/T04 fixes; they do not inspect or clean up a real database. Existing SQLAlchemy legacy API and naive UTC deprecation warnings remain visible. CI uses Ubuntu/Python 3.12; local clean-clone verification uses macOS/Python 3.12.
