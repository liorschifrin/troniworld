## Diagnosis

The revision graph is linear (17 revisions, `3cf0153b0d39` root to `k6l7m8n9o0p1` head, no branches). The history was generated against a database that already existed, so it assumes tables it never creates:

- Root `3cf0153b0d39` adds `user.is_admin` to a pre-existing `user` (NOT NULL, no default). On an empty file: `no such table: user`.
- Later revisions assume `post`, `games`, `points`, `point_players`, `players`, `game_roster`, `events`, `comments`, `article_comments` (all created outside Alembic, apparently by `create_all`). The models' `ix_*` indexes on those tables were never migrated.
- `3ccbad256d39` drops seven legacy tables (`video`, `player`, ...) and `f65e956efdb9` drops the same seven again (plus `player_order_data`). Whatever state a database is in, the second drop fails with `no such table`, so a database stamped at or before `c9c8714eb81b` cannot reach the head with the shipped files. Deployed databases must have been repaired by hand or stamped forward. Not fixable without editing those files.
- `c9c8714eb81b` is named "add events and comments tables" but only creates four indexes.
- Downgrades are unreliable (downgrading a `create_all` schema fails at `DROP INDEX idx_notifs_recipient`), so older snapshots cannot be produced by downgrading.

## Data-loss finding (fixed in `migrations/env.py`)

The app turns `PRAGMA foreign_keys=ON` on every SQLite connection, including the one `flask db upgrade` uses. Batch migrations rebuild a table by dropping it, so rebuilding `games` (`b7d8e9f0a1b2`, `j5k6...`) or `user` (`0d6f3348d878`, `f1a2b3c4d5e6`) cascade-deleted every child row (`points`, `game_roster`, `point_players`, `events`, `comments`, `login_events`, `video_watch_sessions`, ...). Seeded snapshots from 7 of 12 starting revisions lost rows with the old `env.py`. Fix: `env.py` reads and disables the pragma on the raw DBAPI connection, opens one explicit SQLite transaction (`BEGIN`, `transactional_ddl=True`), runs the migrations, and runs `PRAGMA foreign_key_check` inside that transaction before the commit. A violation raises, rolls back all DDL and the version stamp, and the error says the database is at its prior revision. The pragma is restored in a `finally` that never masks the original exception. Round 1 moved the check inside the transaction (it first ran after the commit). The offline `--sql` output contains the table drops and must not be applied to SQLite with foreign keys on. No revision file was touched. Whether deployed databases already lost rows in past upgrades cannot be known here; the user should check.

## Decisions

1. **Baseline strategy: `flask bootstrap-db`** (`flask_app/bootstrap.py`). `create_all` from the models plus a head stamp, refusing any database that has a table. Existing revision IDs and files are untouched; no new baseline revision, because a new root would still need the two legacy-table drops to be skipped. The README's workaround is replaced by this guarded command. (This checkout's README had no workaround text left, only the plain setup; the command is documented in Setup.)
2. **Upgrade path for stamped databases:** `flask db upgrade` from `f65e956efdb9` onward. Older stamps are documented as unsupported by the shipped history.
3. **Drift reported, not fixed.** Pinned in `KNOWN_MIGRATION_DRIFT`: 11 model `ix_*` indexes the migrations never created (login_events, video_watch_sessions, comment_notifications, article_comment_notifications, game_watched), 7 server defaults set by migrations but absent from the models (`user.is_admin`, `user.is_leadership`, `post.created_at`, notification `is_read`/`created_at`), and `idx_notifs_comment_id` in migrations but not the models. A corrective revision would change the schema of deployed databases, so it is left for the user to decide. A bootstrapped database has none of this drift but also has the model indexes and no server defaults, so it differs from a migrated one in those respects.
4. **Snapshots are reconstructed**, from the revision files and models, since real data is off limits.
